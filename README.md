# КОМНАТА СВЕТА — страница гостей (БуФест 2026 · Вход)

**Версия: `guests-v4`**

Мини-приложение для регистрации гостей на входе БуФеста. Три файла —
`vhod.html` (то, что открывают на телефоне у входа), `style.css`
(вынесен из `vhod.html` в `guests-v2`, см. журнал) и `Code.gs`
(бэкенд, Google Apps Script) — плюс сама таблица «Гости-БуФест-2026»
как единственное хранилище данных. Сборки по-прежнему нет: файлы не
компилируются, но `vhod.html` и `style.css` теперь **обязаны лежать
рядом** — по отдельности `vhod.html` откроется без единого стиля.

## ⚠️ Архитектура — это НЕ то же самое, что меню «БуФест» в таблице

У таблицы «Гости-БуФест-2026» уже есть своя логика бронирования прямо
внутри — лист «Бронирование», меню **БуФест** (Забронировать/Отметить
выкупленное/Массово закрыть), скрипт которого хранится текстом на
листе «Google — Интерактив». Это **отдельная, более старая система**,
работает через выделение ячеек на листе «Схема» и требует открытой
Google Таблицы.

**Эта страница (`vhod.html` + `Code.gs`) — параллельная, более новая
система**, рассчитанная на телефон на входе, а не на сидение в
таблице:

- `vhod.html` ничего не знает о ячейках и листе «Бронирование» — это
  самостоятельная HTML-страница с своим `<style>`/`<script>`, которая
  ходит на бэкенд через `fetch()` (POST, JSON, поле `action`).
- `Code.gs` — **отдельный** Apps Script, задеплоенный как веб-приложение
  (`doGet`/`doPost` с параметром `action`), а не как меню/триггер
  выделения. Читает и пишет те же листы показов
  (`10.08 Вий. Домыслы` и т.д.) и общий лист «Выкупленные места» —
  но напрямую по диапазонам ячеек, не через меню.

Обе системы работают **с одними и теми же данными** (листы показов,
«Выкупленные места»), поэтому конфликтов формата стоит избегать в обе
стороны — если меняешь формат записи (например, как выглядит «Ряд /
место») в одной системе, проверяй, что другая не сломается на этом же
листе.

## ⚠️ Правила при любой правке (проверено на собственных ошибках)

1. **`getRange(row, col, numRows, numCols)` — третий и четвёртый
   параметр это КОЛИЧЕСТВО строк/столбцов, не номер и не список
   значений.** На эту грабл наступали дважды на родственной системе
   (меню «БуФест» в самой таблице) — `getRange(lastRow, 1, lastRow, 7)`
   вместо `getRange(lastRow, 1, 1, 7)`. Каждый новый `getRange(...).
   setValues(...)` в `Code.gs` — сверять, что число строк в `data`
   совпадает с запрошенным числом строк в диапазоне.
2. **Правки в `vhod.html`/`Code.gs` не долетают до продакшена сами.**
   Файлы в этом репозитории/выдаче — рабочие копии. Чтобы правка
   реально заработала: `Code.gs` — вставить в редактор Apps Script и
   передеплоить (Разместить → Управление развёртываниями → карандаш →
   «Новая версия»; URL остаётся тем же, но без нового деплоя правки не
   видны); `vhod.html` — загрузить как файл туда, откуда его реально
   открывают на входе.
3. **`SHOWS` продублирован в двух местах** — список показов в
   `Code.gs` (просто строки) и в `vhod.html` (объекты `{tab, title, d,
   dow}`). Название показа (`tab`) должно совпадать в обоих файлах
   **и** с точным названием листа в таблице — если добавляешь/меняешь
   показ, правь во всех трёх местах разом, не в одном.
4. **Проверять синтаксис после правки** — `node --check` на
   извлечённом `<script>` из `vhod.html` и на `Code.gs` (это обычный
   JS, несмотря на расширение `.gs`) — до сдачи, не после того как
   кто-то откроет страницу и увидит белый экран.
5. **Баланс скобок и точечный diff** — как и на основном сайте: перед
   тем как считать правку законченной, сверить diff против предыдущей
   версии и убедиться, что задета только нужная часть, ничего похожего
   на «тут заодно поправил» без явного запроса.
6. **Раскладка схемы зала (`.sectors-row`, `.amphi-wrap`,
   `.amphi-side` и всё, что рисует секторы/амфитеатр/приставные/
   входной/вход-выход) заморожена под эталон `docs/schema-reference.png`
   — не трогать без крайней необходимости.** Эта картинка — не
   иллюстрация, а зафиксированный заказчиком результат нескольких
   раундов правок и откатов (в `guests-v4` ровно так и вышло: правка
   `.amphi-side` на «более аккуратный» компактный стек оказалась
   *неверной* — эталон специально показывает `space-between`,
   растянутый на всю высоту, а не сжатый к верху). Если правда нужно
   что-то поменять в этой части: 1) объясни заказчику, зачем, дождись
   явного «да»; 2) после правки — рендер + попиксельное сравнение с
   `docs/schema-reference.png` (см. ниже), а не проверка на глаз;
   3) если эталон при этом сам меняется — замени и
   `docs/schema-reference.png` тем же коммитом, не оставляй его
   устаревшим.

   Проверка на совпадение (Playwright + Pillow, без реального бэкенда):
   ```python
   # 1. открыть vhod.html, подставить пустые currentGuests/currentSold,
   #    вызвать buildSchema()+setView('schema'), сделать
   #    page.query_selector('#schema-area').screenshot(...)
   # 2. сравнить с docs/schema-reference.png:
   from PIL import Image, ImageChops
   import numpy as np
   diff = ImageChops.difference(Image.open('render.png').convert('RGB'),
                                 Image.open('docs/schema-reference.png').convert('RGB'))
   assert (np.array(diff).sum(axis=2) > 30).sum() == 0  # 0 отличающихся пикселей
   ```

## Структура

```
vhod.html    — разметка + JS (HTML+JS, стили вынесены отдельно)
style.css    — все стили vhod.html, подключается через <link>
Code.gs      — бэкенд, Apps Script веб-приложение (doGet/doPost)
robots.txt   — Disallow: / — страница закрыта от индексации целиком
sitemap.xml  — формальная запись из 1 URL, для единообразия с
               основным сайтом (см. оговорку в журнале, guests-v3)
APP-MAP.md   — карта экранов приложения, для команды, не для
               поисковиков
docs/
  schema-reference.png — замороженный эталон вёрстки схемы зала,
               см. правило 6 выше; не менять без крайней необходимости
README.md    — этот файл
```

⚠️ **`vhod.html` подключает `style.css` относительной ссылкой
(`<link rel="stylesheet" href="style.css">`)** — при загрузке туда,
откуда реально открывают страницу на входе, класть **оба файла в одну
папку**. Загрузить один `vhod.html` без `style.css` рядом — страница
откроется полностью белым текстом без вёрстки, не сразу очевидно
почему.

Установка `Code.gs` описана прямо в шапке файла (комментарий из 6
шагов) — вкратце: таблица должна быть настоящей Google Таблицей (не
`.xlsx`), скрипт вставляется через Расширения → Apps Script,
деплоится как веб-приложение с доступом «Все» (иначе страница входа не
сможет читать данные без входа в Google-аккаунт у каждого на входе),
URL веб-приложения (`.../exec`) вставляется в настройках `vhod.html`
(шестерёнка вверху) один раз — либо сразу зашивается в код через
`DEFAULT_API_URL`, чтобы персоналу вообще ничего не настраивать.

## Данные (структура таблицы «Гости-БуФест-2026»)

**Лист на каждый показ** (`10.08 Вий. Домыслы` и т.д., см. `SHOWS` в
обоих файлах) — гостевой список. Данные со строки `FIRST_DATA_ROW=5`
по `LAST_DATA_ROW=304` (305-я — «ИТОГО», не трогать). Колонки A–G:
Фамилия Имя, Количество мест, От кого, Зона, Ряд/место, Пришёл
(Да/Нет), Примечание.

**«Выкупленные места»** — билеты, проданные не через гостевой список,
общие на все показы. Данные `SOLD_FIRST_ROW=6`..`SOLD_LAST_ROW=900`
(диапазон B6:E900 заявлен в самой шапке листа — с `guests-v1` код
наконец с этим совпадает, см. журнал). Колонки B–E: Показ, Зона,
Ряд/место, Комментарий; F — дата внесения (пишется автоматически).
**Пустое «Ряд / место» = вся зона закрыта целиком** — такую запись
по-прежнему понимает фронтенд при показе схемы (`findSoldEntry`) —
старые записи в этом формате не сломаются. Но заводить новые так
больше не обязательно: предпочтительный способ теперь — «Отметить
продано» → выбрать зону, не указывать место → кнопка «закрыть все N
мест сразу» — она сама пишет N отдельных строк (по одной на место)
через `addSoldBatch`, а не одну запись на всю зону.

## Геометрия зала (константы во фронтенде, `vhod.html`)

```
SECTOR_ROWS = 3, SECTOR_SEATS = 6   — на каждый из 4 секторов (A–D)
AMPHI_ROWS = 10, по 12 мест в ряду  — амфитеатр
```

Ряд 1 в секторе — всегда ближайший к сцене (для A/Б это правый край
блока при отрисовке, для C/D — левый, см. параметр `mirrored` в
`sectorHtml`). Место 1 — всегда ближайшее к амфитеатру. Если геометрия
зала когда-нибудь изменится — менять только эти константы и
переносить формулу `mirrored`, руками пересчитывать не нужно.

`ZONES` — полный список зон (включая «лесенка», «входной»,
«приставные стулья…», не только сектора/амфитеатр — у них нет сетки
мест, `SEAT_BASED_ZONES`/`LOOSE_ZONES` разделяют одно от другого).
`REFERRERS` — список «от кого» для формы, хардкод, руками обновлять
при изменении состава труппы/команды.

менять вёрстку секторов/амфитеатра/приставных/входного без крайней

отличающихся пикселей**. Секторы A/B/C/D и раньше были в порядке (это
чинилось в `guests-v3` или ранее) — ошибка касалась только
`.amphi-side`.

### `guests-v3` — robots.txt, sitemap.xml, карта экранов

По запросу — три файла:

1. **`robots.txt`** — `Disallow: /` целиком. Осмысленно: это рабочий
   инструмент персонала на входе, не страница для посетителей,
   индексация не нужна и нежелательна (форма с именами гостей в
   выдаче — плохая идея).
2. **`sitemap.xml`** — формальная запись из одного URL, для
   единообразия с основным сайтом. ⚠️ **Стоит знать про нестыковку**:
   на основном сайте заведено правило (см. его README) — страницы,
   закрытые в `robots.txt`, **намеренно не входят** в `sitemap.xml`
   (`oferta`/`privacy`/`cookies`/`bot`). Здесь наоборот, по прямой
   просьбе — `robots.txt` закрывает всё, а `sitemap.xml` при этом
   существует. Это никак не вредно (`Disallow` в любом случае сильнее
   рекомендации из sitemap), но если когда-нибудь приводить
   инфраструктуру обеих систем к единому правилу — иметь в виду, что
   это расхождение сделано осознанно по запросу, не по недосмотру.
3. **`APP-MAP.md`** — не для поисковиков, схема экранов и переходов
   внутри `vhod.html` для команды (какой попап от какого действия
   открывается, где что лежит).

⚠️ **URL в `sitemap.xml` — плейсхолдер** (`komnata-sveta.ru/vhod/`).
Реального адреса, где страница входа реально размещена, в переписке
не было ни разу — заменить на настоящий, когда/если он появится.

### `guests-v2` — CSS вынесен в отдельный файл

По запросу — `<style>` (233 строки) вырезан из `vhod.html` в
`style.css`, в `<head>` вместо него `<link rel="stylesheet"
href="style.css">`. Это осознанное отступление от принципа «один файл,
без сборки», описанного в `guests-v1` этого README — раздел
«Структура» выше и правило деплоя обновлены соответственно (нужно
класть оба файла рядом, отдельно `vhod.html` не откроется со стилями).
JS (`<script>`) и разметка не тронуты. Проверено: баланс скобок в
`style.css`, синтаксис `<script>` в `vhod.html` (`node --check`),
diff против `guests-v1` — только замена блока `<style>` на `<link>`,
больше ничего.

### `guests-v1` — README создан, задокументировано накопленное

Первая версия этого файла — более ранняя история правок `vhod.html`/
`Code.gs` до его создания восстановлена по переписке, не идеально
полно (как и у основного сайта — то, что не сохранилось явно, не
восстановить). Основные вехи:

1. **Геометрия секторов** — было `SECTOR_ROWS=3, SECTOR_COLS=3` (9
   мест/сектор), стало `SECTOR_ROWS=3, SECTOR_SEATS=6` (18/сектор, по
   реальному залу). Направление рядов развёрнуто (ряд 1 — к сцене, не
   к амфитеатру), нумерация мест зеркалирована между левыми (A/Б) и
   правыми (C/D) секторами относительно сцены — раньше везде шла
   одинаково слева направо.
2. **Кнопка «входной» отделена от подписи «Вход / выход»** — раньше
   клик по самой подписи двери одновременно регистрировал гостя в
   зону «входной»; теперь это два разных элемента.
3. **Предупреждение о дубликате имени** — при добавлении гостя, если
   Фамилия+Имя уже есть в списке этого показа, форма просит
   подтверждения («Всё равно добавить?») вместо молчаливого создания
   второй записи. Тем же способом — и при повторе имени внутри одного
   группового ввода.
4. **Отмена удаления гостя** — тост с «Отменить» на 4 секунды после
   удаления (как уже было у отметки «пришёл»), включая корректную
   обработку офлайн-очереди (отмена снимает не улетевшее ещё действие
   из очереди, а не просто восстанавливает гостя поверх него).
5. **Баг: пустое «Ряд/место» в «Выкупленных местах» не работало.**
   Таблица обещала («оставь пустым — закроется вся зона»), код
   игнорировал — `findSoldEntry` не матчил ни одно место, если
   `parseSeatInfo('')` возвращал `null`. Починено.
6. **216 отдельных мест вместо 12 записей «весь сектор».** Побочный
   эффект правила из п.5 — общая запись на весь сектор означала, что
   снятие «выкуплено» с любого одного места снимало весь сектор целиком.
   Заменено на честные отдельные записи (6 показов × 2 сектора × 18
   мест). Потребовало расширить `SOLD_LAST_ROW` с 41 до 900 (совпадает
   с тем, что уже было заявлено в шапке самого листа) и убрать с
   дороги нерабочий блок «Массовое закрытие и импорт» (в нём самом
   было написано, что кнопок для него не существует).
7. **`addSoldBatch`** — новое действие бэкенда: закрыть всю зону разом,
   отдельными записями (не одной на всю зону), одним запросом вместо
   N. Кнопка «закрыть все N мест сразу» в форме «Отметить продано» —
   видна только когда зона выбрана, а конкретное место не указано.

С версии `guests-v1` начинается ведение этого файла.

## Дополнение — что было сделано в этом чате (отдельная сессия, не трогает всё написанное выше)

Ниже — честный отчёт конкретно по этой переписке, без правок текста
выше. Часть решений здесь могла позже разойтись с тем, что описано в
основном журнале (другая сессия/веб-версия велась параллельно) —
свежая версия из архива, судя по всему, уже это учла.

**Что построено с нуля в рамках этой переписки:**

   присланному дизайну сайта komnata-sveta.ru, таблице гостей и фото

4. Отображение и правка проданных по билетам мест (лист «Выкупленные

  не дублирует ли она (или не конфликтует ли с) уже готовой.

### Приложение входа (`vhod.html`/`index.html` + `Code.gs`)

- Диагностировал 403 при загрузке данных: показал, что `doGet`/`doPost`
  физически не могут вернуть 403 (всё оборачивается в `try/catch` →
  `jsonOut` с кодом 200) — значит дело не в логике скрипта, а в
  авторизации на уровне Google, до вызова кода. Проверил по присланному
  скриншоту «Управление развёртываниями» — «Выполнять как: Я» и «Доступ:
  Все» стояли верно, это не объясняло 403. Предложил прямой тест
  `/exec?action=list&show=...` в инкогнито-вкладке в обход сайта — по
  этому конкретному пути окончательного подтверждения причины в этой
  сессии не получил, пользователь сообщил, что «что-то поменял и заработало»
  без уточнения, что именно.
- Добавил возможность выбрать место прямо на схеме и сразу открыть
  форму «Новый гость» с предзаполненными «Зона»/«Ряд-место» — раньше

  раньше, открывает карточку гостя. Место, проданное по билету (лист
